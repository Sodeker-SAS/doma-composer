Probar el paquete en local

Cómo modificar sodeker/laravel-attachments y comprobarlo dentro de una aplicación real sin publicar ninguna versión. El ejemplo es FINTEGRA, pero el procedimiento es idéntico en cualquier proyecto que consuma el paquete.

El problema

Por qué no se publica para probar

El camino evidente —publicar una versión y actualizar el proyecto— funciona, pero cobra un peaje que se acumula.

Composer instala las dependencias en vendor/, y ese directorio es territorio suyo: lo borra y lo reconstruye cuando quiere. Editar ahí no sirve de nada, porque el siguiente composer install se lleva los cambios por delante.

Publicar para probar

Cada iteración cuesta un commit, un tag y una descarga. Y deja en el historial versiones que nunca llegaron a validarse, que es justo lo que un historial de versiones no debería contener.

Editar dentro de vendor/

Funciona hasta que alguien ejecuta composer install y el cambio desaparece sin dejar rastro. Es el error clásico de quien empieza, y cuesta horas de depuración porque el código «se revirtió solo».

Enlazar la carpeta de trabajo

Que vendor/sodeker/laravel-attachments no sea una copia sino un enlace a tu carpeta. Editas en un sitio, el proyecto lo ve al instante. Es lo que hace un path repository.

Elegir método

Tres formas, tres alcances

No todas prueban lo mismo. Empieza siempre por la más barata que responda a tu pregunta.

MétodoQué pruebaQué NO pruebaCoste
Pruebas del paquete La lógica: detección de tipos, rutas, resolución de discos La integración real con la aplicación Nulo · ya funciona
Path repository Todo el circuito: formulario, subida, guardado, lectura El comportamiento exacto de un despliegue Dos ajustes, una vez
Tag de prueba El proceso de publicación e instalación tal cual será — Un tag y una descarga por iteración
●

La recomendación práctica

Valida la lógica con las pruebas del paquete, que tardan medio segundo. Monta el path repository para comprobar el circuito completo. Y reserva el tag de prueba —una prerelease como v1.1.0-beta.1— para la verificación final antes de publicar de verdad.

Probar un archivo suelto sin montar nada

Útil cuando la duda es «¿este archivo concreto que sube el cliente pasaría?». Se ejecuta en la carpeta del paquete y usa su configuración real:

comprobación rápida de un archivo
$ cd modulo-adjuntos $ php -r ' require "vendor/autoload.php"; use Sodeker\Attachments\Domain\ValueObjects\{AllowedAttachmentTypes, AttachmentContentType, AttachmentBinary}; $c = require "config/attachments.php"; $a = AllowedAttachmentTypes::fromMap($c["allowed_types"], $c["extension_aliases"], $c["container_markers"], $c["signature_search_bytes"], $c["equivalent_declarations"], $c["opaque_types"], $c["blocked_extensions"]); $f = $argv[1]; $b = AttachmentBinary::fromStream(fopen($f,"rb"), basename($f), filesize($f)); try { printf("ACEPTADO -> .%s\n", AttachmentContentType::resolve($b,$a)->extension); } catch (Throwable $e) { printf("RECHAZADO -> %s\n", $e->getMessage()); } ' -- /ruta/a/respaldo.sql ACEPTADO -> .sql
El concepto

Copia descargada frente a enlace vivo

Es la única idea que hay que entender. El resto son dos ajustes de configuración que se derivan de ella.

↺ Arrastra el divisor de izquierda a derecha para comparar los dos modos.

MODO PRODUCCIÓN MODO DESARROLLO

Modo producción · copia descargada

vendor/ guarda una copia de la versión publicada. Editar tu carpeta no cambia nada en el proyecto: para que lo vea hay que commit → tag → push → composer update.

Modo desarrollo · enlace vivo

vendor/ es un enlace a tu carpeta de trabajo. Guardas el archivo, recargas y ya está: sin commit, sin tag y sin descarga.

En ambos modos la aplicación importa Sodeker\Attachments\… exactamente igual. El código de FINTEGRA no cambia ni una línea. Lo único que cambia es a qué apunta vendor/.

▲

No conviven: es sustitución

Al instalar desde el path, Composer borra la copia y pone el enlace en su lugar. No hay dos versiones activas ni ambigüedad sobre cuál se está ejecutando. Volver atrás borra el enlace y descarga la copia de nuevo.

Montaje

Cinco pasos en FINTEGRA

El proyecto está en LOCALES/FINTEGRA y el paquete en LOCALES/modulo-adjuntos: carpetas hermanas.

1Declarar el repositorio local en composer.json
// FINTEGRA/composer.json — el path va PRIMERO "repositories": [ { "type": "path", "url": "../modulo-adjuntos", "options": { "symlink": true } }, { "type": "vcs", "url": "git@github.com:Sodeker-SAS/doma-composer.git", "no-api": true } ]
Composer busca en orden. Si ../modulo-adjuntos existe, gana; si no —como en el servidor— lo ignora en silencio y usa GitHub. Por eso los dos bloques pueden convivir.
2Abrir la ventana al contenedor
# FINTEGRA/docker-compose.yml php: volumes: - ./:/var/www - ../modulo-adjuntos:/var/modulo-adjuntos
El paquete está fuera de FINTEGRA, así que el montaje ./:/var/www no lo cubre: dentro del contenedor no existiría. La ruta de destino no es arbitraria — ver la sección siguiente.
3Recrear el contenedor
docker compose up -d --force-recreate php
Los volúmenes se fijan al crear el contenedor: reiniciarlo no basta, hay que recrearlo.
4Instalar desde el path
docker compose exec php composer require sodeker/laravel-attachments:@dev
@dev es obligatorio. La restricción del proyecto es ^1.0 y el paquete local resuelve como dev-main —la rama, no un tag—, que no encaja en ese rango.
5Limpiar cachés
docker compose exec php php artisan optimize:clear
Con la configuración cacheada seguirías leyendo la anterior y parecería que nada funcionó.
●

Si la aplicación publicó config/attachments.php

FINTEGRA lo tiene publicado. El provider fusiona la configuración solo en el primer nivel, así que las claves nuevas que añadas en el paquete no llegan solas: hay que copiarlas a mano a la config de la aplicación, o la prueba fallará aunque el enlace funcione. Las aplicaciones que solo usan variables de entorno no tienen este problema.

El detalle que falla

Por qué /var/modulo-adjuntos

La ruta de destino del montaje no se elige: se calcula. Equivocarla deja el enlace colgando y el error es confuso de diagnosticar.

Composer no crea un enlace absoluto, crea uno relativo: ../../../modulo-adjuntos. Tres niveles hacia arriba, contados desde la carpeta que contiene el enlace, que es vendor/sodeker/.

!

Montarlo en /modulo-adjuntos es el error fácil

Parece razonable y es incorrecto: el enlace buscaría en /var/modulo-adjuntos, que no existiría. Composer falla con un enlace roto y el mensaje no señala la causa. Si tienes dudas con otra estructura de carpetas, compruébalo con un proyecto desechable en lugar de razonarlo.

Verificación

Confirmar que es un enlace

Es la comprobación que no conviene saltarse: si es una copia, estarías probando código viejo sin saberlo.

salida real en laravel_app_fintegra
$ docker exec laravel_app_fintegra ls -la /var/www/vendor/sodeker/ lrwxr-xr-x 1 root root 25 laravel-attachments -> ../../../modulo-adjuntos/ $ docker exec laravel_app_fintegra readlink -f /var/www/vendor/sodeker/laravel-attachments /var/modulo-adjuntos # La flecha es la señal. Si ves una carpeta normal (drwxr-xr-x), es una copia.

Comprobar que el enlace está vivo

Una cosa es que el enlace exista y otra que refleje los cambios. Esta prueba lo zanja: escribe una línea en el paquete desde tu Mac y léela desde dentro del contenedor.

prueba del enlace vivo
$ echo "// centinela" >> modulo-adjuntos/README.md $ docker exec laravel_app_fintegra tail -1 /var/www/vendor/sodeker/laravel-attachments/README.md // centinela # Si aparece, el enlace funciona en ambos sentidos. Retira el centinela después.

Probar el comportamiento

Con el enlace confirmado, ya se puede ejercitar la funcionalidad usando la configuración real de la aplicación. Esta es la salida obtenida en FINTEGRA al validar los tipos de archivo:

artisan tinker · config publicada de FINTEGRA
respaldo.sql ACEPTADO -> .sql volcado.dump ACEPTADO -> .dump datos.json ACEPTADO -> .json libro.xlsm ACEPTADO -> .xlsm informe.pdf ACEPTADO -> .pdf mapa.svg RECHAZADO -> extensión no admitida por seguridad trampa.txt RECHAZADO -> se envió como txt pero su contenido es pdf
✓

Prueba las dos mitades

Que lo nuevo se acepte es la mitad fácil. Comprueba también que lo que debe rechazarse se rechaza: un archivo bloqueado y uno renombrado. Una prueba que solo mira el camino feliz no detecta que alguien desactivó una protección sin querer.

Cierre

Volver a modo producción

El paso que más se olvida, y el único que puede romper un despliegue.

!

El composer.lock no se commitea en modo desarrollo

Mientras el paquete venga del path, el lock registra la dependencia como "type": "path" con "symlink": true. En el servidor, composer install obedece al lock al pie de la letra: intentará enlazar a una carpeta que solo existe en tu Mac y el despliegue falla.

Archivo¿Se commitea?Por qué
composer.lockNo, mientras apunte al pathRompe el despliegue
composer.jsonSe puedeComposer ignora el path si la carpeta no existe
docker-compose.ymlSe puedeUn volumen a una carpeta ausente no rompe nada
config/attachments.phpSíNo es de desarrollo: es configuración real de la aplicación

La secuencia de cierre

1Publicar la versión del paquete
# en modulo-adjuntos vendor/bin/pest && vendor/bin/pint git commit -am "…" && git tag v1.1.0 git push origin main --tags
Pruebas y formato antes del tag. Un tag publicado ya no se reescribe.
2Quitar el path y reinstalar desde GitHub
# borrar el bloque "path" de repositories, y después: docker compose exec php composer require sodeker/laravel-attachments:^1.1
Esto borra el enlace, descarga la versión publicada y regenera el lock limpio, que ya sí se commitea.
Soporte

Tropiezos reales

Los tres que aparecieron al montarlo en FINTEGRA por primera vez, con el mensaje exacto y qué significa cada uno.

Qué vesQué pasóQué hacer
Permission denied (publickey) El contenedor no puede autenticarse con GitHub. Casi siempre porque el agente de credenciales del Mac está vacío: no basta con tener la clave en el disco, hay que cargarla. ssh-add --apple-use-keychain ~/.ssh/id_ed25519 y comprobar con ssh-add -l dentro del contenedor.
requires PHP extension ext-soap La aplicación exige una extensión de PHP que su contenedor no tiene. No tiene relación con el paquete: impide cualquier actualización de dependencias. Para salir del paso, --ignore-platform-req=ext-soap. La solución de fondo es añadir la extensión a la imagen.
Enlace roto en vendor/ La ruta del montaje no coincide con la que calcula el enlace relativo. Revisar la Figura 1. El destino es el padre de la raíz del proyecto dentro del contenedor.
Los cambios no aparecen O es una copia y no un enlace, o hay configuración cacheada. ls -la vendor/sodeker/ para ver la flecha; después php artisan optimize:clear.
Funciona el enlace pero no el comportamiento La aplicación tiene su config/attachments.php publicado y le faltan las claves nuevas. Copiarlas a mano a la config de la aplicación.
▲

Si algo falla, el primer comando es siempre el mismo

ssh-add -l. Buena parte de los fallos al instalar desde un repositorio privado se reducen a que la credencial no está disponible, y el mensaje de error rara vez lo dice. Comprobarlo cuesta un segundo y descarta la causa más frecuente.
